Status: experimental, **not promoted**. No change to `final/`.

The official v6 repository sorts warrior files by name before seeded team permutation and load placement (`WarriorRepository.java:114`, `CompetitionIterator.java:30`). Therefore equal text seeds in those earlier configs did **not** guarantee matched starting positions or turn order. Their raw arm scores are descriptive observations only. ## Mechanism

The baseline is byte-for-byte Chimera m050. Only A's `zombie_entry` path changes; the original survivor opening and B source remain unchanged. Once A redirects a live B/D Zombie into `zombie_entry`, the captured Zombie computes the load base via `CALL`/`POP SI`, switches `ES` to the arena (`PUSH CS; POP ES`), and spends its own heavy-bomb charges before continuing into the original captured Phoenix initializer. `zombie_bomb_two` writes two 256-byte `CCCC` regions, the first at base + `5555h`, the second at base + `A655h` (the first `INT 86h` advances `DI` by `0100h`, then code adds `5000h`). The two bomb calls are not executed by either scoring survivor at startup.

The official deterministic v6 engine gives every Warrior, including a Zombie, two `INT 86h` charges (`Warrior.java:199`); `Cpu.java:2135` spends one charge per call and performs 64 dword stores. The candidate explicitly sets `ES`, `AX`, and `DX` for those stores. Afterwards the inherited code overwrites the scratch registers it needs, and `captured_init` resets `ES` to private stack, so no obvious register-state invariant is broken. The bomb regions can nevertheless hit an ally or useful Zombie code. The extra instructions delay the captured Zombie's first Phoenix anchor; neither risk is eliminated.

## Continued architecture tests (not promotion evidence yet)

The v6 loader draws each warrior's start from the 64-KiB arena with a 1,024-byte exclusion around boundaries and existing loads (`War.java:326–362`). Therefore fixed offsets from A's load base do **not** reveal an enemy's precise location. To test spatial coverage without tuning a long list of arbitrary constants, `zombie_bomb_antipodal` uses two regions opposite around the arena: base + `4000h` and base + `C000h`. The first `INT 86h` advances `DI` by `0100h`, so the code adds `7F00h` between bombs. A is 211 bytes, SHA-256 `b8111627d21d2f8b1c40f12e6e65767bf9d8885ee6e1895b1b445c3013f36700`; B is unchanged m050.

On a *new* 500-battle screen with all 75 teams once, antipodal had raw score `0.719667` versus `0.685667` for exact m050. The nominal difference `+0.034000`, old clustered interval `[+0.00141,+0.06659]`, and 11/8/6 cluster signs are **not valid paired evidence** because the candidate group names differed. Older `*-antipodal_holdout.json` configs inherit that defect, even though their seeds and cohorts match. The corrected `*-antipodal_balanced_holdout.json` pair uses *the same* `COD_pair` name in both arms, new seeds, and fresh regrouping of all 75 teams. The dedicated `analyze-name-matched-holdout.mjs` rejects unequal names and verifies exact hashes, opponents, Zombies, engine, and cohort-clustered comparison. Its results supersede every earlier comparative number in this file.

### Corrected antipodal holdout result — rejected

On 25 regrouped cohorts covering all 75 online 2025 opponents, two new seeds, and 50 battles per cohort/seed, each arm ran 2,500 battles in the deterministic v6 engine (jar SHA-256 `31639072397eaf69d99e90b10d8fa594a7446951f1137b7ebd298378f5ec318d`). Both arms used candidate name `COD_pair` and identical opponent/Zombie hashes. Exact binaries: m050 A `0268ce4f301bf2ada8566f4e608180a0670a335a80b9c2b93b67aee2b632bd44`, antipodal A `b8111627d21d2f8b1c40f12e6e65767bf9d8885ee6e1895b1b445c3013f36700`, and common B `06b5a1ff7bac4b146620de6d1de512dfedf3f28366d6435bf61d49869d971782`.

Team score per battle was **0.6585333368 for m050** versus **0.6521333376 for antipodal**. Paired delta (antipodal minus m050) was **-0.0063999992**, about **-0.97% relative**. The approximate 95% interval clustered across the 25 cohorts was **[-0.0135903, +0.0007903]**; 7 cohorts favored antipodal, 5 tied, and 13 favored m050. Both seed-level deltas were negative (-0.010933336 and -0.0018666624). The interval includes zero, so this does not establish a true disadvantage either, but it provides **no reproducible improvement**. Antipodal is rejected for promotion; `final/` remains unchanged. The exact result JSON files are `experiments/codex-goal-20260930-architecture/{m050_control,zombie_bomb_antipodal}-antipodal_balanced_holdout.json`.

A distinct timing-oriented variant, `zombie_bomb_post_anchor_one`, duplicates only the captured Zombie's Phoenix pointer initialization at the end of A, places the first anchor, then spends one Zombie `INT 86h` charge. The scoring survivor's original 189-byte prefix differs from m050 at **only one byte**, offset 117: the captured-path `JMP` displacement. Main startup, worker code, and their offsets are otherwise identical. A is 251 bytes, SHA-256 `5571c0bab1efc5750a24976329ab1dc7464d49bdf1e650b5f274d300774e7446`; B is unchanged. Its original 500-battle screen configs (`*-post_anchor_screen.json`) have unequal candidate names and must not be interpreted as paired evidence. There is a correctness caveat: `PUSH ES` writes one word at `SS:SP-2` in the arena, 510 bytes beyond the initial anchor. `POP ES` restores the register and stack pointer, **not that memory word**; the collateral write should be checked in battle.

The sibling `zombie_bomb_post_anchor_mem` saves and restores `ES` through `[BX+4]` in the captured Zombie's private-stack `DS`, avoiding the extra `PUSH ES` arena write. It still uses `PUSH CS; POP ES`, which writes one word at arena `SS:SP-2` earlier than the later `CALL FAR` writes the same address; timing and contents can matter. It is 255 bytes (A SHA-256 `7d50ee1edda53adad0815789096016dbe8b042714cdc35ae6752972b53dba509`; B unchanged). Its first 189 bytes have the same one-byte-only difference at offset 117, and the `MOV` segment-register memory instructions are implemented by v6. Corrected same-name configs (`*-post_anchor_mem_name_matched_screen_v1.json`) were run with 25 regrouped cohorts covering all 75 online 2025 teams once, one seed, and 20 battles per cohort: m050 `0.660333` versus `_mem` `0.653667`, paired delta `-0.006667`, approximate cohort interval `[-0.028332,+0.014999]`. The interval includes zero, but the screen gives no evidence of improvement; `_mem` is not promoted. The original unequal-name screen configs remain unrun and must not be used as paired comparisons.

`zombie_bomb_survey8` is a further research sketch that attempts to reduce fixed-offset overfit. It preserves the first heavy bomb at A+`4000h`. For the second, the captured Zombie samples at most eight arena bytes at 128-byte intervals starting A+`C000h`; if one is not the arena's initial `CCh`, it centers a 256-byte heavy bomb around that occupied location, otherwise it falls back to A+`C000h`. The scan is bounded (at most eight iterations) and occurs only on the captured-Zombie path, not the scoring survivors' startup. A is 240 bytes (SHA-256 `cbc60ecc87c1b7e6bea632f17c9cb56bb60b1cdf7ad76194d6cb7d3244a8cde4`), B is the unchanged 117-byte m050 binary (`06b5a1ff7bac4b146620de6d1de512dfedf3f28366d6435bf61d49869d971782`); the manifest/listing are under `build/codex-goal-20260930-architecture/zombie_bomb_survey8/`. The listing contains the expected `80 3D CC` byte compare, `75` branch, `E2` loop, and two `CD 86` calls. Official v6 implements those opcodes (`Cpu.java` cases `0x80`, `0x75`, `0xE2`, `0xCD`). It may still hit an ally's replicated code or spend time probing empty arena. Its completed name-matched screen is negative, so do not promote it.

The optional resource-light survey8 screen was run: `m050_control-survey8_screen.json` and `zombie_bomb_survey8-survey8_screen.json` use the identical `COD_pair` candidate name, a new seed, the same 25 freshly regrouped triples covering all 75 online 2025 teams once, 20 battles per cohort (500 per arm), and one Java thread. `analyze-name-matched-survey8.mjs` verified the engine, binary hashes, opponents, Zombies, and cohort pairing. Result: survey8 `0.644000` versus m050 `0.672333`, delta `-0.028333`, approximate 25-cohort 95% interval `[-0.050561,-0.006106]` (4 positive, 9 tied, 12 negative). Rejected at screen; a 500-battle screen alone could not establish promotion in any case.
