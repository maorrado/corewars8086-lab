# Benchmark speedup (2026-10-01)

Why: the original research goal (a pair better than both m049 and m050 *on average over
the full all-2025 field*) needs many matched seeds per candidate, which was too slow
(one 10-seed screen of one warrior = 12,500 battles, about 14 minutes).

## Result

| Workload | Before | After | Speedup |
|---|---|---|---|
| One full 10-seed screen config (250 runs, 12,500 wars), `bigcheck-m050` | 852.3 s (official harness, original engine, Java 8) | 89.8 s (`fast-benchmark.mjs`, Java 8; mean of 2 alternating runs) | **9.5x** |
| same | 852.3 s | 66.6 s (`fast-benchmark.mjs`, Java 25 + ParallelGC; mean of 2 alternating runs) | **12.8x** |
| A real 9-config research batch (2,250 runs, 112,500 wars) | ~2.1 h (9 x 852 s) | 831 s (Java 8, incl. ~4 min of input copying since removed) | ~9x |
| 10 verification cases (500 wars), interleaved, median of 3 | 33.3 s (original, one JVM per run, 4 threads = how screens ran) | 8.9 s (batch, 8 threads, Java 8) | 3.7x (small batch, less amortization) |

Results are **byte-identical** to the original engine run with `--parallel=false`
(the deterministic reference), on Java 8 and on Java 25. See "Correctness" below.

How to use:
`node fast-benchmark.mjs --threads 8 --spot-check 3 [--java C:/Users/ronyr/.jdks/openjdk-25.0.1/bin/java.exe --jvm-opts "-XX:+UseParallelGC"] cfgA.json cfgB.json ...`
Same config format and same result-file schema as `official-benchmark.mjs` (which is
unchanged). All runs of all given configs run in ONE JVM on one shared thread pool.
`--spot-check N` re-runs N evenly spaced runs with the original engine (sequential, on the
config's Java 8) and aborts on any byte difference. `--java`/`--jvm-opts` only change the JVM
of the batch (default: the config's Java 8). Run directories default to
`build/fast-runs/<experimentId>`; inputs are copied once per cohort (not once per seed) into
`<runDirectory>/_inputs/`. Configs that set a different engine `jar`, or `telemetry`, are
refused (not reproduced), and two configs of one batch may not share a run directory.

## What changed

Engine copy: `repos/corewars8086-6.0.0-fast` (the original `repos/corewars8086-6.0.0-deterministic`
is untouched and remains the reference).

1. **Alive-group count without allocation** (`War.countAliveSurvivorGroups`). The original
   built a stream + HashSet on *every round* whenever exactly two survivors were alive (a
   very common long-war state, up to 200,000 rounds). Replaced by a small loop with the
   same result (same filter, distinct group names by `equals`).
2. **Direct event dispatch** instead of the reflection `Proxy` multicaster
   (`CompetitionEventMulticaster`, `MemoryEventMulticaster`: copy-on-write listener arrays,
   same add/remove/equals semantics). The proxy ran on every round (`onRound`, `onEndRound`)
   and on every memory write, with boxing, an `Object[]` per call and a shared flag written by
   all threads.
3. **`UnsyncRandom`**: the exact `java.util.Random` LCG (same seed scrambling, same `next(bits)`),
   without the atomic compare-and-set per draw (each war owns its Random; never shared).
4. **Arena initialization** with `Arrays.fill` on the linear range instead of 65,536 address
   objects + checked writes per war (done before the listener is attached, as before).
5. **Headless runs disable memory-write events** (no memory listener can exist headless).
6. **Precomputed permission-region bounds** (regions are fixed when a warrior is created).
7. **Parallel mode made deterministic**: wars still run concurrently, but each war's awards are
   recorded and added in war-id order, the exact float addition order of sequential mode. The
   original added them in completion order, so its last float digit depended on scheduling
   (46 of the 250 official `bigcheck-m050` runs differ from sequential in the last digit).
   A failing war now aborts the competition instead of being silently dropped. Wars that never
   ran (GUI abort, or the 1 h timeout) still contribute nothing, as before. Self-review caught
   that an earlier version of this change would have waited forever on them; fixed and
   re-verified.
8. **Telemetry bookkeeping skipped when no telemetry file is written** (it was only read by the
   telemetry writer; in parallel mode it was a HashMap shared by all worker threads).
9. **`BatchRunner`** (new main class): many runs ("jobs", each given by its ordinary CLI
   arguments) in one JVM. Each job plans its wars with the same iterator and seeds as
   `runCompetition` (`Competition.planCompetition`), all wars of all jobs go to one pool, and
   each job's awards are applied in war-id order when its last war finishes.
10. **`fast-benchmark.mjs`**: drop-in harness for the above (same inputs as
    `official-benchmark.mjs`, deletes stale score files first, one JVM per batch).
11. **Input preparation**: the official harness copies and hashes 12 files for every run
    (2,250 runs = 27,000 copies + hashes, ~25 s per config). The fast harness hashes each
    source file once and copies inputs once per cohort, shared by that cohort's seeds
    (the engine only reads them; its one modification, `fixFiles`, is idempotent and all jobs
    are loaded before any war runs). Verified: 250/250 runs identical to the per-run-copy
    version. Preparation is now a few seconds.

## Measurements per change (ablation)

Ablation build (`repos/corewars8086-6.0.0-ablation`, not used for research): each change can be
switched back to the original code with `-Dcw.orig.<name>=true` (static final flags, so the
JIT removes the unused branch). Workload: BatchRunner, 1 thread, the 10 cases (500 wars), so
JVM start-up is excluded and only engine speed is measured. Every one of the 28 runs was
byte-identical to the reference.

Round 1 (quiet machine):

| change | revert only this one (all others new) | apply only this one (all others original) |
|---|---|---|
| (none / all) | all new: **15.0 s** | all original: **21.7 s** |
| alive-group count | 23.4 s | **15.3 s** |
| event dispatch | 17.7 s | 21.6 s |
| Random without CAS | 15.5 s | 20.2 s |
| arena fill | 15.3 s | 20.1 s |
| memory events off | 15.0 s | 24.1 s |
| region bounds | 14.6 s | 21.9 s |

Round 2 ran while the laptop was thermally throttled (CPU reported ~800 MHz; the same
configuration varied from 14.6 s to 45 s within the round), so it is only a cross-check: same
ordering (all new 22.1 s vs all original 27.8 s; revert-only-count 45.1 s; apply-only-count 28.9 s).

Reading: the alive-group count was by far the main engine cost; alone it recovers nearly all
of the engine gain. Direct dispatch is the second (about +18% when reverted). The Random and
arena-fill changes are small (2-3%). Memory events off and precomputed region bounds are not
measurable (kept: exact, harmless). Engine changes together: about 1.45x single-thread.
The rest of the 8.5x comes from running everything in one JVM (start-up and JIT warm-up once
instead of per run, ~3.4 s per run before) and from the shared pool (no idle cores at the
end of each run).

Threads: batch with 8 threads vs 4 threads on 4 cores / 8 logical: 8.9 s vs 9.4 s (about 5%).

## Correctness

Reference: the original engine with `--parallel=false` (fully deterministic).

- 10 varied real cases (4 different warrior pairs, light and heavy cohorts, 10 seeds):
  fast engine byte-identical in sequential mode and with 1, 2, 4 and 8 threads; the original's
  own parallel mode was NOT (5 of 10 cases differ from its sequential output in the last digit).
- BatchRunner: all 10 cases in one JVM: identical; each case 3 times in one JVM (30 jobs):
  identical (no state leaks between jobs).
- Ablation: all 28 combinations of original/new code paths: identical.
- Full config through `fast-benchmark.mjs` (`bigcheck-m050`, 250 runs) vs the official result:
  204 runs textually identical, 46 differ only in the last float digit (max relative 2.4e-7;
  aggregate 1.4e-9). All 46 were re-run with the original engine in sequential mode:
  **46/46 byte-identical to the fast output**, i.e. the differences were the original parallel
  mode's own nondeterminism. Plus 5 spot checks inside that run: identical.
- Every research batch runs with `--spot-check` (original engine, sequential, byte compare).

Reuse safety: nothing about game state is cached. The only things reused across jobs are the
warmed-up JVM and loaded classes. Each job reads its own warrior files and builds its own
Competition/WarriorRepository; each war gets fresh memory, CPU state, warriors and seeded Random.
Warrior code is copied byte by byte into each war's own arena (`War.loadWarriorGroup`); the
shared `WarriorData` arrays are only read, so self-modifying code or memory writes cannot
leak into another war or job. The precomputed permission bounds come from region objects that
are fixed for the warrior's lifetime (final endpoints; no code path changes them), so memory
writes or code changes by warriors cannot make them stale.

## JVM version and flags (isolated experiment)

Other JDKs already on the machine were only invoked by path (nothing in `tools/` or in any
active configuration changed): Temurin 21.0.12 (VS Code Java extension), OpenJDK 25.0.1
(`~/.jdks`). Workload: BatchRunner, 8 threads, the 10 cases x2 (1,000 wars), 2 interleaved
rounds, every output byte-checked (`build/speedup/jvm-experiments.sh`, log next to it):

| JVM / flags | round 1 | round 2 |
|---|---|---|
| Java 8 default | 16.3 s | 16.4 s |
| Java 8 `-XX:-TieredCompilation` | 15.8 s | 13.4 s |
| Java 8 `-XX:+AggressiveOpts` | 17.6 s | 14.2 s |
| Java 8 `-XX:MaxInlineLevel=15 -XX:InlineSmallCode=2500` | 16.2 s | 14.1 s |
| Java 8 `-Xms2g -Xmn1g` | 15.1 s | 15.0 s |
| Java 21 default (G1) | 13.3 s | 12.6 s |
| Java 21 `-XX:+UseParallelGC` | 12.5 s | 11.2 s |
| Java 25 default (G1) | 14.0 s | 11.5 s |
| Java 25 `-XX:+UseParallelGC` | 12.7 s | 10.8 s |

The Java 8 flags are within noise. On the full config (12,500 wars, alternating):
Java 8 91.7 / 87.8 s, Java 25 + ParallelGC 68.2 / 64.9 s, i.e. **1.35x**, all 250 runs
byte-identical each time. Java 25 + compact object headers was slower (59.8 s vs 47.7 s in a
single cool-CPU pair) and is not used.

Why a newer JDK cannot change the score files here: game logic is integer arithmetic,
`java.util.Random` is specified exactly, the shared RNG of the combination iterator is a
library class, and directory listing order comes from the OS. The one known risk is
`Float.toString` (its algorithm changed in JDK 19) and the score files are written with
`"" + float`. `build/speedup/floatcheck/FloatFormatCheck.java` formats **every** float in
[0.125, 1024) plus 0.0 (109,051,904 values) and hashes them in blocks of 65,536: Java 8,
Java 21 and Java 25 produce identical hashes for all 1,665 blocks. Scores here are 0 or
at least 1/8 (at most 8 surviving warriors) and at most 2 x battles per run, so the check
covers every possible score value for configs with up to 512 battles per run.

## Considered and not done (documented, not worth it now)

- **Allocation-free memory path in the CPU emulator** (linear addresses instead of a
  `RealModeAddress` object per byte access; the operand decoder stores each address in a field,
  so it always escapes). Profile after the changes: `call far`/`push` paths ~60%, `nextRound`
  ~17%, `INT 87h` scan ~7%. Expected another 1.2-1.5x, but it touches every memory access of
  the emulator and its exception order (permission checks between the two bytes of a word),
  so the verification cost is high. A 10-seed screen of one warrior already takes ~100 s.
- **`INT 87h` scan** (up to 65,536 checked word reads per call): limited by the 1 bomb per
  warrior; same risk argument.
- **Caching results**: baselines are computed once per seed set and reused by comparing
  result files (no recomputation needed for later candidates on the same seeds); no run-level
  cache was built.
