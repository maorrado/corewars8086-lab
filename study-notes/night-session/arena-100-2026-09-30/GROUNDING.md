## Engine facts (verified from source, not guessed)

The engine's Java source lives at `repos/corewars8086-6.0.0/src/main/java/il/co/codeguru/corewars8086/` if you want to verify anything yourself (`cpu/Cpu.java`, `memory/`, `war/War.java`). Everything below has already been verified against it.

### Memory model
- Each warrior gets its OWN private stack segment and a small GROUP-SHARED memory region (1024 bytes, shared between your A and B only).
- There is ONE shared 64KB "arena" segment (`ARENA_SEGMENT = 0x1000`, confirmed from `War.java:21`) that every single warrior's CODE is loaded into, at different offsets. This is where replication and combat actually happens.
- The arena starts filled with `0xCC` bytes (`ARENA_BYTE`, `War.java:30`) everywhere nothing has been written yet.
- `MIN_GAP = 1024` bytes is the ONLY guaranteed minimum spacing between any two loaded warriors (`War.java:36`). Later-loaded warriors (load order is RANDOMIZED per battle, see below) face tighter placement constraints as more warriors compete for the same 64KB space. Don't assume more spacing than this if you write anything position-relative.
- Execute permission is segment-specific: you can only EXECUTE code in the arena segment. Attempting to execute code in your own stack segment or the shared-memory segment throws a fatal exception.
- **Execute blind spot**: `CS = 0xFFC` (the segment value used by the existing champion lineage's far-call replication mechanism) has TWO separate unreachable-for-execution linear-address ranges: IP in `[0, 0x3F]` and IP in `[0xFFC0, 0xFFFF]` (both verified correct by hand — these are genuinely different linear addresses, not a restatement of one). If you use any similar far-call/segment-aliasing trick, watch for this. A real 2025 competitor (`HRZ_Registered_Winners2`) died trying to execute at exactly this blind spot.
- **16-bit memory access is TWO independently-permission-checked byte writes**, not one atomic operation, even for a single non-REP instruction (verified: `AbstractRealModeMemory.java` implements `readWord`/`writeWord` as two sequential byte calls). If your target address is one byte before a permission-region boundary, the low byte can commit successfully and then the warrior dies on the high byte — a partial write already happened. Leave at least 1 byte of margin from any region boundary for word-sized operations near an edge.
- Segment:offset addressing wraps modulo 1MB (`linearAddressFull % 0x100000`), not modulo 64KB — classic real-mode aliasing is possible (different segment:offset pairs can resolve to the same linear address). If you try anything with unusual segment values, the actual reachable linear address is `segment*16 + offset`, mod 1MB — verify this by hand, it's easy to get wrong.

### Timing / turn order (THE MOST IMPORTANT MECHANIC)
- Exactly ONE opcode executes per living warrior per round. No variable-cost model — a 1-byte instruction and a 20-byte instruction both cost exactly one round. This applies even to not-taken conditional jumps.
- There IS a per-round "extra opcode" bonus roll for each living non-zombie warrior (based on its energy/speed), but it draws from a SINGLE SHARED random-number stream for the entire battle (`War.java:213-218`, `War.java:416`). This means: the exact number of "extra opcode" rolls consumed each round depends on how many warriors are alive that round, which depends on which specific opponents you're facing and how the battle unfolds — the same seed value under different opponent compositions produces genuinely different downstream randomness from the first death onward. Don't assume "same seed = same underlying dice roll sequence" across different opponent sets.
- Turn ORDER within a round (which warrior's A/B pair goes first relative to other TEAMS) is randomized once per battle at load time (via the same shared RNG) and then locked for that battle's entire duration. Your own A always executes before your own B (within your team), but there's no fixed "team 1 always first" rule across teams.
- Load order across all warriors in a battle is ALSO randomized (Fisher-Yates style) via the same shared RNG.
- `MAX_ROUND = 200000` is a hard ceiling — a battle that hasn't resolved scores whatever survivor state exists at that point. Not likely to matter for a fast replicator, but exists.

### Scoring (verified exact formula)
- Score = `1.0 / numSurvivorsAlive`, and this is added **once per surviving INDIVIDUAL warrior**, not once per team (`War.java:406-414`). If BOTH your A and B survive to war-end, your team earns DOUBLE what a team with only one surviving member earns, holding everything else equal. Do not design B as a disposable/passive bootstrap-then-idle warrior — B surviving is worth exactly as much as A surviving. Give B real, active defense too.
- `isOver()` (the war-ending condition) explicitly EXCLUDES zombies from the survivor count (`War.java:162-178`). You do not need to hunt down every last zombie to win — the war ends the instant you are the last non-zombie surviving GROUP, regardless of how many uncaptured hostile zombies remain wandering.

### INT87h — the "smart search-and-patch" opcode
- Searches the ENTIRE shared arena segment (all 65536 byte-offsets) for a 4-byte pattern: `AX:DX` treated as two 16-bit words read via `ES:[DI+diff]` and `ES:[DI+diff+2]`. On the FIRST match found, it OVERWRITES those same 4 bytes with `BX:CX`, then stops (breaks out of the search loop). It does NOT report the match location back to any register.
- **This is completely FREE, timing-wise, regardless of hit or miss or how far into the 65536-byte scan the match is found**: the whole search-and-patch runs in exactly ONE round (verified: `Cpu.java:2153-2177`, the entire `for (int i = 0; i <= 0xFFFF; ++i)` loop is inside a single `int87()` Java method call, itself one opcode dispatch). This is a genuine anomaly versus the strict one-opcode-one-round rule everywhere else — a single `INT 87h` can do up to 65536x the "work" of a normal opcode for the same one-round cost.
- `STD`/`CLD` (direction flag) reverses which direction from DI the scan proceeds (`diff = directionFlag ? -i : i`).
- Verified directly from source: `int87()` READS `m_state.getDI()` but never calls `m_state.setDI(...)` anywhere in the method — DI is provably unchanged by the call itself. This matters if you're reasoning about what DI holds after an `INT87h` call.
- The champion lineage uses TWO separate `INT87h` calls with DIFFERENT purposes: one in `start:` (a one-time, first-load-only call, searches for a specific stall-loop-in-blank-arena pattern that we verified matches ZERO real 2025 opponents — this exact search was tried as a retargeting opportunity tonight, see "Known trap" below), and one in `zombie_entry:` (fires only when resuming as a captured zombie, searches for a different pattern to re-establish self-recognition after capture).

### Zombies
- A file whose name ends in the letter "h" (case-insensitive) gets a 2x zombie-speed multiplier on top of the global `--zombieSpeed` setting, purely from the filename — silent, not from its code content (`WarriorRepository.java`, `War.java:123-126`). The standard zombie roster used in this project's tests (`zom20a`-`zom20d`) does NOT trigger this.
- Zombies are excluded from the survivor count for both scoring and the war-ending condition (see above).

### Opcode-level landmines (textbook-8086 assumptions that DON'T hold in this engine)
- `0x26` (the `ES:` segment-override prefix) is completely UNIMPLEMENTED — throws a fatal exception. No `[es:xxx]`-style operand ever works. Only implicit-ES instructions (`STOSW`/`MOVSW`/`INT87h`) can touch the shared arena segment.
- 16-bit `RCR` updates NEITHER Sign, Zero, nor Parity flags — only Carry and Overflow. 16-bit `SHL`/`SHR`/`SAR` update Zero flag ONLY, not Sign or Parity (inconsistent with their own 8-bit counterparts, which DO update all three). **Never trust Sign/Parity flags immediately after a 16-bit shift or rotate in this engine — use an explicit `CMP reg,0` or `TEST reg,reg` afterward if you need a real conditional branch on those flags.**
- Overflow flag is never correctly computed for ADD/SUB-family opcodes (known pre-existing engine limitation, not something you caused).
- The virtual `NRG` opcode requires TWO literal consecutive `0x9B` bytes to be recognized. A single stray `0x9B` anywhere in your executable code is a guaranteed-fatal unsupported opcode, not a silent no-op.

## Known bug classes — all found and paid for tonight, do not repeat

These are extremely easy to reintroduce if you're not careful. Read every one.

### Bug class 1: register value persists across `call far [bx]` replication generations
If your design uses a `call far [bx]`-style indirect far-call for self-replication (the champion lineage's exact mechanism — a warrior writes its own replication anchor bytes into the arena, then jumps through it to "become" the next generation), understand this precisely: **the far-call does NOT re-run your bootstrap between generations.** It transfers control with whatever register state existed at the exact moment of the jump. Any register your replication loop body WRITES to (intending it as a one-time or per-cycle value) will carry that written value into every subsequent generation, silently, forever — UNLESS you either (a) never write to that register inside the loop at all, (b) restore it explicitly before anything downstream reads it expecting the original value, or (c) bake the value as an IMMEDIATE operand directly in the instruction (immediates get freshly re-copied into every generation via your own template-copy code, so they can never be "leftover" from a prior generation).

Concretely: a design that tried to give a stride-toggle mechanism its own delta value (separate from an existing constant reused for two purposes) by doing `mov dx, <newDelta>` inside the replication loop CRASHED 100% deterministically, every time, regardless of what specific delta value was chosen — because `dx` was also being read by an unrelated instruction on the NEXT generation expecting its original bootstrap value, and the write from generation N leaked into generation N+1's read.

### Bug class 2: byte-length changes must update ALL coupled copy-count constants
If your replication loop body (`worker:`-equivalent) copies itself into the next generation's location via a REP-prefixed string instruction (`rep movsw`), the copy COUNT (`mov cx, N`) is a magic number tightly coupled to the exact BYTE LENGTH of that loop body. **Any change to the loop body's byte length (adding/removing/resizing an instruction) requires you to recompute and bump EVERY site that sets this copy count** (there may be 2-3 such sites: the one-time bootstrap's own template-save, a separate zombie-capture-resume path's template-save if you have one, and the loop's own self-refresh of the count each generation) to at least cover the new length, rounded up to the nearest even byte count (since `movsw` copies 16-bit words, not bytes). Missing even ONE of these sites silently truncates what gets copied into future generations — the anchor bytes or trailing logic get cut off, and the corruption doesn't manifest as an immediate crash; it manifests many generations later when the truncated/wrong data is finally read, making it hard to trace back to the real cause if you don't check this proactively.

**Always verify by checking the actual assembled byte length via the `.lst` NASM listing file** (produced alongside the binary by the assembler — see "How to build" below) rather than hand-counting, and cross-check every coupled copy-count site by hand every single time you touch the loop body's length.

### Bug class 3: filler-byte padding is ONLY safe in regions execution jumps OVER, never at a label execution lands on
If you remove an instruction and want to keep a file's total byte length unchanged (e.g., to avoid touching coupled offsets elsewhere), it is tempting to pad the gap with inert filler bytes (like `0xCC` repeated). **This is only safe if the gap sits in a region your control flow explicitly JUMPS PAST — never at any label that is itself a jump target or fall-through destination**, because execution lands there and runs the "filler" as real opcodes. `0xCC` specifically is the `INT3` opcode, which is UNSUPPORTED by this engine and fatal the instant it's executed.

This was tried twice tonight and produced two different failure severities: one crashed 100% deterministically and immediately (since the corrupted label was hit on essentially every single battle). The other was far more dangerous — it did NOT crash a 400-battle smoke test at all, because the specific code path it corrupted only executes on a RARE mid-battle event (zombie capture) that the small smoke sample never happened to trigger; it only surfaced once a much larger (2500-battle) test finally hit that rare path, at which point the aggregate score cratered. **A clean smoke test does NOT prove correctness for any code path gated behind a rare or conditional event — only a full-scale test, or a test specifically designed to force that path, can confirm it.**

If you genuinely need to remove bytes from a location execution runs through sequentially (not skips over), the safe options are: (a) let the file's total byte length actually shrink and carefully recompute every coupled downstream offset/copy-count by hand (verified against the assembled `.lst` listing, not assumed), or (b) replace the instruction with a DIFFERENT real, genuinely harmless instruction of the identical byte length (not inert filler).

### Bug class 4: successfully triggering an effect on a live opponent doesn't guarantee it helps you — verify the actual net effect, not just "did it work"
A well-motivated, carefully-verified idea (searching for a byte pattern common in real opponents' code and corrupting it, using the free `INT87h` search) was tried tonight with TWO different, both-verified-safe replacement strategies. Both produced a large, real, systematic REGRESSION (roughly -16% on the full screen) versus not doing it at all — despite passing every safety check (no self-harm, no crash, no shared-state corruption, confirmed via debug-tracing that neither version died differently from the unmodified baseline on identical seeds). **The root cause was never fully identified** — it's suspected to be some effect in aggregate competitive dynamics (changing which real opponents die when, in a way that nets unfavorable for your own scoring) rather than any bug in the implementation, but this was not confirmed. The practical lesson: verifying a mechanism is SAFE (doesn't crash, doesn't corrupt your own state) is necessary but NOT sufficient to conclude it HELPS — you must measure the actual net effect on the full screen score before believing an idea is a real improvement, no matter how well-reasoned it seemed beforehand. Don't report an idea as working just because it didn't break anything.

### Known-safe reference facts (already established, use freely)
- A toggle/delta constant used to perturb a fixed value (e.g., alternating a replication stride between two values) MUST have a ZERO LOW BYTE if it's going to interact with or be XORed against any value whose low byte must stay fixed at a specific pattern the design's self-recognition depends on (e.g., a fixed `0xA2` signature byte used throughout the champion lineage). A nonzero low byte on such a toggle previously caused a catastrophic regression (score dropping from ~0.78 to ~0.06) by corrupting that fixed low-byte pattern. If your design has any similar fixed-signature-byte dependency, respect this.
- The stride-toggle idea itself (alternating a self-replication step/stride between two different values each generation, via a self-inverting operation like XOR so it returns to the original after 2 applications, no drift) is a proven, real mechanism for beating m049/m050 in DIRECT head-to-head combat — but it has an inherent, unavoidable "magnitude-mismatch" cost on the general screen that scales with how different the two stride values are from each other. A version using a moderate ~47% ratio between the two strides scored close to but still measurably below both m049 and m050 on the screen (0.6547 vs 0.6674/0.6723) while still beating both of them in direct combat. Values further from moderate (either much more extreme or much closer to 1:1) tested WORSE, not monotonically better as you approach 1:1 — the relationship between stride ratio and screen score is NOT smooth or predictable; it behaves more like a memory-address collision lottery against the specific real opponent field than a continuous cost function. If you explore this specific mechanism, do not assume a "closer to 1:1 is always better" extrapolation — it was tested and falsified.
- A single, tiny, genuinely dead instruction (`xor di,di` when DI is already provably 0 and nothing reads it before it's re-zeroed) removed from a ONE-TIME bootstrap path was confirmed to save exactly one engine round and produce a small but real, positive, and reproducible screen-score improvement (~0.5-0.7%) — this is the entire, sole, verified source of advantage the m050 reference warrior has over m049. If you find similarly dead instructions in your OWN bootstrap, removing them (correctly — see bug class 3 above) is low-risk, low-but-real reward. Not every dead instruction has the same value though — one similar removal, later in the bootstrap sequence rather than very early, measured as a statistically-indistinguishable-from-zero null result despite being equally "correct."

## How to build and test your design

Work in your own unique output directory: `candidates/generated/arena-100-2026-09-30/candidate-<YOUR_ID>/` (use the exact candidate ID you were assigned in your task prompt — this keeps your files from colliding with the other ~99 agents working in parallel in this same repository).

**Assembling** (produces a `.lst` listing file alongside the binary — always check this for exact byte offsets when reasoning about byte-length coupling):
```
node assemble.mjs <your-output-dir>/build <your-output-dir>/YourA.asm <your-output-dir>/YourB.asm
```
This uses a headless-browser-based NASM. Check the JSON output for `"size"` (exact byte count per file) — you have a 256-byte budget per file, well above what the champion lineage uses (it's under 200 bytes), but don't assume you need to use all 256; correctness matters more than size.

**Crash-checking (ALWAYS do this before trusting any score)**: run a SMALL battle count (e.g. 50-100 battles across 2-4 real opponent cohorts) first. A team score of exactly 0.0 across many battles means a crash, not "your design is just bad." Real, working designs produce varying, nonzero scores even when they're not great. Build a small config JSON (see the existing pattern in any `config-*-smoke.json` file in the repo root for the exact schema) and run:
```
node official-benchmark.mjs <your-smoke-config.json>
```

**Full screen test (the number that actually counts)**: once crash-free, run the FULL 25-cohort/2-seed structure (2500 battles) to get a trustworthy score comparable to the reference baselines (0.6674 for m049, 0.6723 for m050). The exact reusable cohort/opponent/zombie structure already exists — copy `config-synth-v9-all2025.json` from the repo root, change only `experimentId`, `outputPath`, `runDirectory`, `candidate.name`, and `candidate.warriors` (point at your own assembled binaries), then run:
```
node official-benchmark.mjs <your-full-screen-config.json>
```
Read the resulting JSON's `aggregate.teamPerBattle` — that is your comparable score.

**If you hit a crash or suspicious result**: do not guess-and-check randomly. Trace the actual cause — read your own assembled `.lst` listing carefully, check every register write against every later read (the exact discipline that found and fixed every bug class documented above), and if still stuck, there is a debug-trace-capable build of the engine at `repos/corewars8086-6.0.0-debug-trace/` that can print exact death round/offset/byte-context (see any existing `-Ddivtrace.warriors=...` invocation elsewhere in this repository's history for the exact command pattern, or ask — the pattern is: copy your two binaries into a debug survivors directory alongside dummy filler opponents, then invoke the debug-trace jar with `-Ddivtrace.warriors=YourTeam1,YourTeam2`).

## Reference: the current best-known design (v9), for orientation only

The champion lineage (m049/m050 and everything derived from it) works via: a one-time bootstrap that computes a quantized signature byte from the warrior's own load address, writes a 2-byte "anchor" (`call far [bx]`, opcode bytes `FF 1F`) at a computed position in the arena, then repeatedly self-replicates by copying its own code forward and jumping through the anchor to "become" the next generation — while an `INT87h` call periodically re-asserts/repairs that anchor if corrupted. This is ONE proven architecture, not the only possible one. You are free to build something completely different from scratch if you believe another approach can beat both reference scores — a from-scratch design that clearly beats 0.6723 on the full screen is just as valid a submission as an improvement on the existing lineage. Don't feel constrained to only tweak the existing design; genuinely novel architectures are explicitly welcome and may be more likely to find something the existing lineage's local-optimum tuning cannot.
