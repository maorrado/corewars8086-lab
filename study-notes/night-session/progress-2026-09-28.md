## Update: mechanism CONFIRMED via instrumented Java engine (empirical, not inferred)

The browser single-stepping above was inconclusive because the browser and
Java engines use different PRNGs, so battles cannot be cross-reproduced. This
was resolved properly: built a debug-only fork of the deterministic engine
(`repos/corewars8086-6.0.0-debug-trace`, copied from
`corewars8086-6.0.0-deterministic`, NOT touching the official checkout or
`final/`) that hooks `onWarriorDeath` and dumps 33 bytes of arena memory
centered on the dying warrior's `CS:IP` at the exact moment of death, using
`War.getMemory()` (unrestricted access, for diagnostics only).

Re-ran the *exact* recorded battle (`all-v1-01`, seed `all-001`, same
warriors directory used by the original telemetry run) and confirmed
byte-for-byte identical telemetry output vs. the original run (SHA-256
match) before trusting the new trace output — the engine's determinism is
solid.

Captured 57 death traces (48 CPU exceptions, 9 memory exceptions) in this one
cohort/seed. Decoding the byte dump around the fatal address (accounting for
the fact that the recorded `IP` telemetry field is the address *at* the
exception, and the instruction that actually faulted starts one byte
earlier) gives an unambiguous result:

- The dominant recurring context (29/48 = 60% of CPU exceptions) is:
  `... C7 47 02 FC 0F [37] A4 03 10 ...` immediately following the
  `mov word [bx+2], 0FFCh` instruction that is part of Chimera's own
  `phoenix_pointer_ready` sequence.
- Compared against the known-correct bytes at that exact source location
  (`31 F6 89 C7` = `xor si,si; mov di,ax`), only **4 bytes differ**:
  `31 F6 89 C7` → `37 A4 03 10`. Everything from the next instruction onward
  (`B8 FC 0F 8E C0 89 FC ...` = `mov ax,FAR_SEG; mov es,ax; mov sp,di; ...`)
  is byte-identical to the original Chimera code.
- `0x37` is `AAA`, which `Cpu.java` marks `// TODO: AAA` and throws
  `UnimplementedOpcodeException` — this is the actual fatal instruction. It
  is immediately fetched after the corrupted 4 bytes are reached by Chimera's
  own live `CS:IP`.
- Disassembling the opponent in this specific battle
  (`A_AVI_Fishandpoultry1`, 75 bytes) shows it is **itself a far-call/replicator
  family survivor**: `REP MOVSW`, `MOV WORD [BX+2],0x1003`, `MOV [BX],DI`,
  `XOR SI,SI` — structurally the same class of strategy as Chimera. This is
  two independently-scheduled replicators writing into the same 64 KiB arena;
  the corruption is not a bug in Chimera, it is a **collision between two
  live writers**, where the opponent's write front happens to land exactly on
  Chimera's 4-byte `xor si,si; mov di,ax` sequence inside a live band before
  Chimera's own `CS:IP` reaches it.

**This changes the actionable conclusion.** It is not "the far-call chain
outruns its own write front" (that earlier hypothesis is now superseded —
retracted a second time, this time with hard evidence). The real, confirmed
mechanism is: **a single 4-byte sequence (`xor si,si; mov di,ax`, the two
instructions immediately after `mov word [bx+2],FAR_SEG` in
`phoenix_pointer_ready`) is a single point of failure per band** — if any
opponent writer's front (of *any* kind, not a targeted attack, just ordinary
sparse/dense writing) touches those 4 bytes before Chimera's own execution
reaches them, the entire band dies immediately via an unimplemented-opcode
exception, specifically because the corrupted first byte happens to decode as
`AAA` (0x37) in this exact corruption pattern. Other single-byte
corruptions at the same site would likely be similarly fatal (most byte
values decode to *something* semi-plausible only at low probability; `CCh`,
segment-prefix bytes, and several others are also fatal on their own).

This is a genuinely new, evidence-backed finding not previously written up
in `optimization-2025-report.md`'s search history (which covered copy-size,
phase, segment, gap, and signature changes, but not "reduce the blast radius
of a single corrupted byte inside the steady-state per-band bootstrap").

### Second, independent death mechanism found in the same trace set

The remaining CPU-exception traces (16/48) form a second, distinct pattern:
`CC...CC F1 [random-byte] 00 00 CC...CC` — almost the entire 33-byte window
is still-untouched arena filler (`CCh`), with only `F1` (offset -1 from
recorded IP) plus two stray bytes nearby. `0xF1` is `Cpu.java`'s literal
invalid-opcode case (`// 0xF1 - invalid opcode`), confirmed as the actual
fatal byte using the same off-by-one correction as the first cluster (the
telemetry `IP` field is recorded *after* the fatal byte is fetched).

Unlike the first cluster, this is **not** self-corruption of Chimera's own
code — the surrounding bytes are not a recognizable fragment of
`ChimeraA.asm`/`ChimeraB.asm` at all. The most consistent explanation: the
far-call replication chain (`CALL FAR [BX]`) landed on a band that is almost
entirely unwritten, containing only a small foreign scrap (plausibly a
stray word from an opponent's own heavy bomb (`INT 86h`) or sparse writer
passing through). This corroborates the earlier `chimera-boot-round40.png`
browser observation (Chimera ending a battle with `IP` sitting inside raw
`CCh`) — that hypothesis was prematurely retracted after the single-step
sampling was inconclusive, but this independent Java-engine evidence now
supports it as a real, separate death mode alongside the 4-byte
self-corruption cluster.

**Net conclusion: there are (at least) two distinct, independently confirmed
failure modes**, each responsible for roughly a third of observed CPU
exceptions in this one cohort/seed sample:

1. **Self-corruption of a fixed 4-byte sequence** (`xor si,si; mov di,ax`,
   immediately after `mov word [bx+2],FAR_SEG` in `phoenix_pointer_ready`)
   by an opposing writer's front passing through a live band before
   Chimera's own `CS:IP` reaches it. ~60% of CPU exceptions in this sample.
2. **The replication chain's `CALL FAR [BX]` landing on a still-unwritten
   (or nearly so) band** — i.e., the call target for a new replication step
   is computed and jumped to before that band actually contains valid
   Chimera code, encountering `CCh` filler (or a stray foreign byte) instead.
   ~33% of CPU exceptions in this sample.

Both are consequences of the same underlying design tension already
identified in the lesson material (item 15/20/21 in `study-notes/README.md`):
"the decisive risk is the latency and distance between the live CS:IP and
future bytes already written into the arena." Neither is a simple
off-by-one bug fixable by changing one constant; both point toward needing
either (a) tighter coupling between when a band is written and when it is
jumped into (reduce the window where `CALL FAR [BX]` can land on a band that
isn't fully ready), or (b) redundancy at the specific 4-byte
`phoenix_pointer_ready` choke point so a single foreign write there doesn't
kill the whole band.

Went back to precisely re-align the 29-case death context against the exact

using a systematic byte-array shift search instead of manual counting (the
manual approach produced at least two different wrong answers earlier in
this session — first "launcher vs worker mismatch" [retracted], then "xor
si,si at worker+0xB7" [also appears wrong, see below]).

Systematic result: the death-adjacent bytes align, at shift=+3, with source
offsets `0x91` onward (`mov ax,FAR_SEG` / `mov es,ax` / `mov sp,di` / ...),
and the 3 bytes immediately before that match position (source `0x8D-0x90`,
i.e. `xor si,si; mov di,ax`) are where the foreign/corrupted bytes
(`37 A4 03`) sit instead of the expected `31 F6 89 C7`. This part is a solid,
mechanical byte-alignment result, not a guess.

**However**, offsets `0x86`-`0xAB` (`phoenix_pointer_ready`, including this
`xor si,si; mov di,ax` pair) are — per the source itself — part of the
**one-time bootstrap** block. `phoenix_pointer_ready` is only reached once,
via `jmp short phoenix_init`/`captured_init` from `start:`, and every
subsequent band is entered via `worker: ... call far [bx]` jumping straight
into a *copied* `worker:` block (source offsets `0xAC`-`0xBD`, containing its
*own*, differently-located `xor si,si` at `0xB7`). The `rep movsw` that
seeds each new band copies exactly `worker:`'s 9 words (`0xAC`-`0xBE`), which
does **not** include `phoenix_pointer_ready`'s bytes at `0x86`-`0xAB`.

This means the corrupted bytes identified above should only be able to exist
at the warrior's **original, fixed `loadOffset`** (where the full 189-byte
binary is first placed and never overwritten by its own replication), not at
the quantized/replicated band addresses. But the 29 death traces occurred at
6+ visibly different `IP` values (`0x10A3, 0xF0A3, 0x4CA3, 0xE0A3, 0x70A3,
0x88A3`, ...) that all share the low-byte pattern `xA2`/`xA3` consistent with
the `quantize()` formula's fixed `AL=0xA2` output — which is exactly the
formula used to compute `loadOffset`'s *own* first band target, not
necessarily distinct replicated bands elsewhere.

**Open contradiction, not resolved tonight**: either (a) `CS:IP` can somehow
return to/re-execute the original `loadOffset` copy of
`phoenix_pointer_ready` (which would require an explanation I don't have —
nothing in the traced control flow re-enters it after the first `jmp short`),
or (b) the quantize formula, applied to different random `loadOffset` values
across different battles/warriors, simply produces many different
`0x3C`-aligned target addresses that all happen to end in `0xA2` by
construction (since `AL` is hardcoded to `0xA2` in every quantize call, in
*both* the one-time bootstrap and — need to re-check — possibly also reused
verbatim, not just structurally similarly, somewhere I haven't traced), and
what's actually being hit repeatedly across "different" `IP`s is genuinely
the *same* `phoenix_pointer_ready` block, just at different `loadOffset`
values per battle (i.e., 29 different battles, each corrupting its own
warrior's fixed original-location bootstrap code, not 29 corruptions across
many bands within one battle). Explanation (b) is more consistent with the
evidence (recall: the 29 traces were aggregated across `war=0` through

## Update: mechanism CONFIRMED precisely — the `FF 1F` band-start anchor is the single point of failure

Added `loadOffset` and a full per-war `LOADMAP` line to the debug trace
build. Computed the exact quantized band-address chain by hand from
`COD_m049tel1`'s actual `loadOffset=0x6869` in `war=0`, using the same
formula traced from source (`AH=(loadOffset_high/0x3C)*0x3C+0x10, AL=0xA2`,
then each subsequent band = previous − `0x3C00`):

`chain = 0x4CA2, 0x10A2, 0xD4A2, 0x98A2, 0x5CA2, 0x20A2, ...`

The observed death `IP=0x10A3` is exactly `chain[1] + 1` — i.e., band #2 in
the sequence, offset by the same "+1" correction already established (engine
records `IP` *after* the fatal byte is fetched). **This conclusively places
the fatal byte at the band's start offset itself (`xxA2`), not at
`phoenix_pointer_ready`'s or `worker:`'s internal `xor si,si`.**

The band-start byte is exactly where `STOSW` (with `AX=0x1FFF`) writes the
two bytes `FF 1F` — a `CALL FAR [BX]` instruction that is the anchor every
subsequent replication step calls through to re-enter that band. The
observed corrupted bytes at that position (`37 A4` instead of `FF 1F`) mean
**this 2-byte anchor was overwritten before Chimera's own call chain used
it**, killing the chain at that link.

**This is the confirmed, final mechanism for the dominant (60%) CPU-exception
death cluster**: a single 2-byte value (`FF 1F`, the `call far [bx]` written
by `STOSW` at each new band's start address) is the *entire* mechanism
holding each replication band alive. If any opponent's write (whether
targeted or merely a passing sparse/dense writer, `INT 86h` bomb, or another
replicator's own band) touches either of those 2 bytes before Chimera's
chain calls through them again, that band — and everything chained through
it — is permanently lost. There is no redundancy, no decoy, and no
alternate path back into a band once this anchor is damaged.

The second cluster (`F1`/mostly-`CCh`, ~33% of CPU exceptions) is a related
but distinct failure: the call chain reaching a band whose `FF 1F` anchor was
never written at all (or is otherwise still filler), which is consistent
with the anchor-fragility finding — both point to the same 2-byte
`call far [bx]` re-entry point being the load-bearing, unprotected
single point of failure of the entire Phoenix replication design.

## DEC DI ablation experiment (as directed) — result: DEC DI is NOT dead code, hypothesis was WRONG

Per direction, ran a controlled empirical test instead of continuing manual
analysis. Built `candidates/generated/chimera-decdi-test/ChimeraA-nodecdi.asm`
— byte-identical to `final/ChimeraA.asm` except `worker:`'s trailing `dec di`
(1 byte, `4F`) is removed (188 bytes vs. 189). Paired with the unchanged
`final/ChimeraB.asm`.

**200-battle screen result: candidate's Warrior A scored 0.000000 in every
single one of 20 cohorts** (`experiments/nodecdi-screen-200.json`) — not a
partial regression, complete and consistent failure.

Used the instrumented debug-trace engine (same one built earlier, target
group name updated to `ChimeraA`) to find the mechanism. Result:
**`ChimeraA1` dies at exactly round 476 in every single war, regardless of
random `loadOffset`** — fully deterministic, not opponent-dependent. This
immediately falsifies my "DEC DI is unread dead code" hypothesis: something
about DI's post-STOSW value or the resulting byte layout genuinely matters.

**Root cause identified**: `worker:` is 17 bytes long (odd number). Every
band's `rep movsw` copies exactly `9` words = **18 bytes** (`mov cl,9` /
`mov cx,8` + 1 for the first `movsw`), i.e. the copy has always included
**1 spare byte** past the real end of `worker:` — apparently harmless in the
original m049 because that spare byte happens to be the very first byte of
the *next* band's `FF 1F` anchor sequence (which gets correctly overwritten
by the next `STOSW` anyway before it's ever used as an anchor). Removing
`dec di` shortens `worker:` to 16 bytes, so the fixed 18-byte copy now
includes **2 spare bytes**, pulling in one additional byte of stale/garbage
content that was not intended to be copied. This corrupts something
(probably the `worker:` copy stored in the private stack, whose exact
following byte layout I have not yet traced) in a way that only manifests
after enough repeated iterations (round 476 constant across all seeds/loads),
consistent with a slow, deterministic accumulation rather than a one-shot
crash.

**Conclusion for future candidates**: `worker:`'s exact byte length is
load-bearing and tightly coupled to the hardcoded `9`-word copy count
throughout the design (`mov cx,8` + first `movsw` in the bootstrap, `mov
cl,9` in `worker:` itself). **Any edit to `worker:`'s instruction count or
encoding must be paired with a matching recalculation of the copy count**, or
must be verified to not change `worker:`'s byte length at all. This was not
previously written up this explicitly in `optimization-2025-report.md` (the
existing "reduce copy from 20 to 18 bytes" experiment there changed the copy
count deliberately and measured a net-neutral score result; it did not
document *why* a mismatch is catastrophic, which this ablation now shows:
100% Warrior-A death, not a mere shift in score). This is useful negative
knowledge but does **not** by itself point to a viable improvement — the
`DEC DI` reorder/removal idea is now conclusively rejected, not just
unverified.

**This also means the earlier "single point of failure" story (the `FF 1F`
band-start anchor) is confirmed once more from a different angle**: the
whole design is extremely sensitive to exact byte-count bookkeeping between
`worker:`'s real length and the copy size, which is consistent with it also
being fragile against external corruption of the same bytes.

## Candidate screening round 3: band low-byte (AL) sweep — REJECTED, 100% Warrior-A death, mechanism not fully resolved

Tested whether the fixed `AL=0xA2` constant (the low byte of every quantized
band address, identical across every band/battle/survivor of this family)
is an exploitable, predictable signature. Substituted `AL` at both quantize
sites (`start:` and `zombie_entry:`) with 6 alternative even values (`0x00,
0x42, 0x62, 0x82, 0xC2, 0xE2`) via direct source substitution
(`candidates/generated/chimera-al-sweep/`), keeping `ChimeraB` unchanged.

**200-battle screen: Warrior A scored exactly 0.000000 in every cohort for
all 6 values tested** — a complete, deterministic failure, not a partial
regression (same signature as the earlier `DEC DI` ablation failure).

Used the instrumented debug-trace engine again (round filter removed to
catch round-0 deaths too) and found: death is **deterministic at round
~202-204 regardless of `loadOffset`** across multiple wars — ruling out
opponent-collision as the cause, same as the `DEC DI` case. `reason=memory
exception` (not CPU exception), at the *first* quantized band (verified by
recomputing the quantize formula by hand from the recorded `loadOffset` and
matching the death `IP`'s high byte exactly).

Decoded the exact bytes at the band-start address: `02 4C FC 0F` repeating
every 4 bytes, **not** the expected `FF 1F FF 1F` anchor pattern. Traced the
linear-address math for the `ES=FAR_SEG` write (`es*16 + di`) and confirmed
it resolves to a valid in-arena address for both `AL=0xA2` and `AL=0x00`
(`0x14C62` and `0x14BC0` respectively, both inside `0x10000-0x1FFFF`) — so
the write target itself is not out-of-bounds by that mechanism, ruling out
my first hypothesis (linear-address overflow from the `ES` alias).

**Mechanism not fully resolved** — did not identify why the actual band
bytes become `02 4C FC 0F` instead of the STOSW-written `FF 1F`, or what
specifically triggers a memory-access violation (as opposed to the
unimplemented/invalid-opcode CPU exceptions seen elsewhere). Ran out of time
budget for further manual tracing on this one. Given the extremely
consistent, deterministic, 100%-fatal result across 6 different `AL` values,
there is no ambiguity about the *practical* conclusion even without the
full mechanism: **`AL=0xA2` must not be changed without deep further
investigation the lab does not have time for tonight.** Rejected, same
confidence level as `DEC DI`.

**Combined lesson from both `DEC DI` and `AL` ablations**: `final/ChimeraA.asm`
and `ChimeraB.asm` have multiple non-obvious internal invariants (exact
`worker:` byte length vs. copy count; something about `AL`'s specific value
vs. `0x00`/other alternatives) that are not documented anywhere in
`optimization-2025-report.md` or the source comments, and are NOT safe to
assume are arbitrary/cosmetic constants. Any future candidate touching
`phoenix_pointer_ready`/`worker:`/the quantize sequence should budget time
for an ablation-style empirical check (small `battlesPerCombo`, watch for
`w1`/`w2` collapsing to exactly `0`) before investing in a full screen.
